# Правило версіювання yt-dlp BD

Застосунок використовує тризначну внутрішню версію `MAJOR.MINOR.PATCH` і
чотиризначну публічну версію `MAJOR.MINOR.PATCH.HOTFIX` для GitHub Release.

## Виправлення — збільшуємо PATCH

Якщо реліз лише виправляє помилки, стабільність, швидкість, сумісність,
безпеку або іншу наявну поведінку, збільшуємо публічний PATCH на один і
скидаємо HOTFIX до нуля.

Приклад: public `0.3.2.0` / Tauri `0.3.20` стає public `0.3.3.0` /
Tauri `0.3.30`, а tag — `v0.3.3.0`.

## Терміновий hotfix — збільшуємо HOTFIX

Якщо власник прямо визначає виправлення як hotfix поточної публічної версії,
збільшуємо четверте число.

Tauri підтримує лише тризначний SemVer, тому його внутрішній PATCH утворюється
як `PUBLIC_PATCH * 10 + HOTFIX`. Компонента HOTFIX має бути від `0` до `9`.

Приклади:

- public `0.5.1.1` → Tauri `0.5.11`;
- public `0.5.2.0` → Tauri `0.5.20`;
- public `0.5.2.1` → Tauri `0.5.21`.

Таке відображення зберігає правильний порядок версій для автоапдейтера. Старі
релізи до запровадження правила можуть мати нескодовану внутрішню версію;
починаючи з `0.5.1.1`, усі нові релізи зобов’язані використовувати це правило.

## Нова функція — збільшуємо MINOR

Якщо реліз додає хоча б одну нову функцію для користувача, збільшуємо середнє
число на один, а PATCH скидаємо до нуля. Це правило діє і тоді, коли разом із
новою функцією реліз містить виправлення.

Приклад: public `0.3.2.0` / Tauri `0.3.20` стає public `0.4.0.0` /
Tauri `0.4.0`, а tag — `v0.4.0.0`.

## Як застосовувати правило

- Версію визначаємо за найбільшою зміною всього майбутнього релізу, а не
  збільшуємо окремо для кожного commit.
- Лише виправлення — PATCH, якщо власник прямо не визначив його як hotfix.
- Внутрішній Tauri PATCH завжди кодує `PUBLIC_PATCH` і одноцифровий `HOTFIX`:
  `PUBLIC_PATCH * 10 + HOTFIX`.
- Хоча б одна нова функція, навіть разом із виправленнями — MINOR.
- Зміни тільки в документації або внутрішньому релізному процесі не вимагають
  окремого релізу застосунку. Вони входять до найближчої версії.
- `package.json.version`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` і
  запис застосунку в `src-tauri/Cargo.lock` завжди містять однакову внутрішню
  версію.
- `package.json.releaseVersion` містить публічну чотиризначну версію, а
  `RELEASE_NOTES.md` обов’язково називає саме її.
- Перед запуском manual release workflow усі версії, notes і tag мають бути
  узгоджені в одному PR.

Після кожного bump обов’язково перевіряємо всі поточні джерела версії:

- `package.json`: `version` і `releaseVersion`;
- `package-lock.json`: кореневі `version`;
- `src-tauri/Cargo.toml` і запис застосунку в `src-tauri/Cargo.lock`;
- `src-tauri/tauri.conf.json`;
- `RELEASE_NOTES.md`;
- `.github/workflows/release.yml`: `workflow_dispatch.inputs.tag.default`;
- актуальні release-приклади в `docs/START_HERE_UK.md`,
  `docs/GITHUB_RELEASE_HANDOFF_UK.md` і `READMEAI`.

Опис поля `workflow_dispatch` навмисно використовує універсальний приклад
`vX.Y.Z.H`, а його `default` завжди містить поточний public tag і відразу заповнює
поле в GitHub Actions. Release-тест автоматично перевіряє узгодженість усіх
поточних значень вище.

MAJOR-версію до `1.0.0` або вище змінюємо лише окремим свідомим рішенням для
великого несумісного релізу, а не автоматично.
